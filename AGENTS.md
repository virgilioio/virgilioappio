
- Client pipeline links live at /cp/:token (not /p/, which serves legacy job-post links); the pipeline-public function delegates dossier rendering to dossier-public via an internal service-key call so there is one client-ready serializer.
- Gio Fit auto-generation is scoped to jobs with a live client pipeline view via fit_analysis_queue + process-fit-queue (wake-on-enqueue, bounded hops, no cron) — keeps AI cost limited to candidates clients will open.
- Public pipeline section payloads are allowlisted and serialized only by `pipeline-public`; anonymous users never read candidate, offer, or rejection tables directly — prevents PII and internal workflow leakage.
- Analytics dates hires/offers/rejections by hired_at/offered_at/rejected_at via `eventAt()` in src/lib/analyticsEventDates.ts, never updated_at — updated_at moves on any edit.
- Pipeline hygiene metrics are current snapshots from usePipelineAgingMetrics (stage entry = latest of entered_stage_at / last stage-history move, else date added, flagged estimated) and ignore the date range — keeps 'time in stage' honest.
- Analytics reads of potentially large tables go through fetchAll/fetchAllIn in src/lib/fetchAllRows.ts — the API caps responses at 1,000 rows, which silently undercounted widgets.
- Job hiring slots live in job_openings (Req ID unique per workspace); status (open/offer/filled) is derived in job_openings_with_status and jobs.target_fill_date is trigger-derived from open openings — never store status or edit target_fill_date directly.
- Offer and hire flows must select a job_openings row; hiring and unhiring go through atomic database functions so slot state, candidate status, and Req ID remain consistent under concurrent edits.
- The candidate Create/Edit Offer experience uses one 820px three-step right sheet; configured offer-form fields stay data-driven and retain their existing bindings, validation, drafts, openings, and approval behavior.
- Gio Sales is a separate app/backend: all traffic goes through HMAC-signed (`GIO_LINK_SECRET`) edge functions (`sales-*` inbound, `integration_outbox` → `deliver-integration-outbox` outbound); deal-linked openings are capped by `job_sales_lines.hires` and cancelled, never deleted — keeps both apps' fee math consistent.
- Job attribution: the hiring-team pool lives in job_assignments (unique per job+user+role; many Sourcers/Recruiters), each filled opening credits one Sourcer and one Recruiter via mark_hired, and deal jobs' Sales/ES live in jobs.sales_team written only by Gio Sales — the draft→open publish gate is enforced in the database, so the UI only mirrors it (src/lib/jobTeam.ts).
- Draft jobs: setup completeness and the draft→open gate come only from the database's job_setup_checks (UI renders its result, never recomputes), and drafts from Gio Sales can only be cancelled from the deal — keeps the publish rule in one place.
- Gio Sales is the master client list: ATS client organizations are mirrored via the signed `sales-company-upsert` function, never created or edited in the ATS, and the CRM/deals UI is removed — avoids two diverging client lists.
- Req IDs are assigned only by the database (per-workspace req_id_counters via allocate_req_ids in a job_openings insert trigger; never editable, never reused) — keeps IDs unique across ATS and Gio Sales openings.
- Google Workspace connect/reconnect/disconnect has one flow (src/lib/googleWorkspaceConnect.ts + GoogleWorkspaceConnection card, disconnect via disconnect-google-workspace), reused by Email & calendar and Integrations — keeps both screens consistent and reachable by every role.
- Edge functions answer CORS with the caller's allowlisted Origin (wrap handlers in withRequestCors from _shared/cors.ts), never a fixed default — a fixed origin blocked every other Gio domain.
- Google Workspace OAuth state is sealed server-side (_shared/mailOAuthState.ts: user, PKCE verifier, redirect base, opener origin) and /mail/oauth/callback is public — the popup can finish on any allowed Gio address without a session there.
- Motion, feel and robustness follow CLAUDE.md (Block B §1–§15 adopted from Gio Sales, 2026-10-09): motion tokens in src/index.css, one Sonner toast system, the ATS keeps its own visual identity — keeps both apps feeling the same without restyling the ATS.
- Find, Phase 0 (2026-10-11): a sourcing project's shortlist / not a fit / archive / collected state lives in sourcing_project_candidates (keyed by project + Apollo id), never in the search cache, so a 24h refresh never loses work; candidates are unique per (tenant, apollo_id); Collect and every Apollo call take the user and workspace from the token (_shared/caller.ts), match LinkedIn/email with find_tenant_candidate before creating anyone, and write what Apollo charged to apollo_credit_ledger — the balance (app and server) is apollo_credit_status() on Apollo's own cycle (apollo_credit_plans: Virgilio 5,000 a month, renewing on the 19th). Collect skips the phone (1 credit); "Collect with phone" / "Get phone" ask for it through a per-workspace signed apollo-phone-webhook URL. The cross-workspace "Gio" lane is removed.
- Find, Phase 1 (2026-10-12): every way a person enters (Collect, applications, the extension, manual add, CSV import) asks find_candidate_matches() first — through _shared/matchCandidate.ts on the server and checkForDuplicateCandidate in the app. Only a strong match with no conflict (same Apollo id, LinkedIn or email, nothing contradicting) merges without asking; applications also need the name to match unless LinkedIn matched; phone alone is never enough. Everything weaker is created and raised in Possible duplicates on Candidates (possible_duplicate_pairs(); "Not the same person" stops a pair coming back). person_identities holds every key and follows a merge. Find shows our own candidates first (search_candidates(), with pipeline history and the rule-based fit score in _shared/findCriteria.ts), then PDL, then new from Apollo; people already in the linked job are left out. Motive candidates were moved into Virgilio once (candidate_transfers), with no tag: they are Allan's own work.
- Find, Phase 2 (2026-10-12): a project has three tabs: Results, Shortlist and Collected. Shortlist and Not a fit are free, shared with everyone who can open the project, applied at once with Undo (useProjectPeopleActions), and stored on sourcing_project_candidates with a snapshot of the person, so they outlive the search cache; people in Gio are kept by candidate id. AI fit (shortlist-ai-fit) scores the shortlist only and stores ai_fit_* with the fingerprint of the search and job it was scored against; the score on Results is the rule-based Fit. Sourced people enter a job at job_entry_stage() (Application Review, else the first stage) everywhere. "Find people like this" (src/lib/findSimilar.ts) seeds a new search from someone in Gio. The talent pool: projects with pool_enabled (nine seeded: SDRs, AEs, revenue leaders × LATAM, US, EMEA) plus searches linked to open jobs; pool-builder runs hourly 13–22 UTC from pg_cron with a key kept in Vault (pool_builder_secret_matches), spends an even daily share of credits above the 1,000 reserve (all of it in the last 3 days of the cycle), only on people new to Gio, fit 55+, at most 25 per company per cycle, without phones, through enrich-apollo-profile in service mode (ledger note 'Talent pool'), pauses when a recruiter collects 10+ in an hour, logs talent_pool_runs and sends admins a Monday summary (notification category talent_pool). Read an Apollo person's company with apolloCompany() (_shared/apolloPerson.ts): Apollo moved it to organization.name.
- Find, Phase 3 (2026-10-12): outside data about someone we already have (Apollo collect or refresh, résumés, applications, Talent, phone webhooks, the Chrome extension) is written only through apply_candidate_update() (server: _shared/candidateUpdate.ts applyCandidateUpdate; client: rpc with source 'resume' only). Never update title, company, location, email, phone, LinkedIn, name, salary or bio from a source with a plain update. candidates.field_provenance records each field's source and age; the zz_candidates_provenance trigger writes it (a signed-in edit = person, nobody can write the column directly). A person's edit, an unknown value from before tracking and a merge choice are never replaced; name, email, phone and LinkedIn are fill-only (other emails and phones join contact_emails/contact_phones); a résumé, application or extension value under 30 days old beats Apollo. current_job_title and role_current move together. A new company (same_company() ignores Inc/SA de CV etc.) or a new title is a job change: old role into candidate_work_experience, a candidate_job_changed activity, and candidate_update notifications for the team on open jobs where the person is active and the people who shortlisted them (not the one who pressed Refresh); the same change isn't reported twice in 30 days. Apollo search previews refresh title and company for free (trigger on sourcing_preview_candidates). refresh-candidate-profiles: the profile's Refresh · 1 credit (Sources block), and a daily pg_cron run at 12:15 UTC for pipeline and shortlist people with nothing fresher than 90 days, within apollo_credit_plans.refresh_cap_credits a cycle (ledger kind 'refresh', note 'Scheduled refresh'). Merges go through merge_candidate_payload_tracked.
